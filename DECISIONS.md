# Implementation decisions

## Chapter continuation — Step B

- Closing a chapter requires a separate confirmation and an owner-scoped, version-checked transaction. A restart uses a separate server function that refuses to replace a chapter started on another device.
- A finished account sees history and settings without an active plan; starting another goal reuses onboarding. Existing reminder preferences remain on the device, but scheduled notifications are cancelled. Other devices cancel when they next refresh.
- Historical trees are calculated read-only from the same distinct completed-day rule used by the database. Archived milestones are never modified; the displayed tree is a reconstruction from the loaded journal.

## Chapter continuation — Step A

- A chapter is a linked new season; existing seasons and milestone constraints are unchanged. Reflection answers are transient and not stored with the plan. Separate, versioned consent is required before sending them to Gemini; withdrawing AI consent clears it.
- A failed AI draft cannot silently become a local plan. The local alternative requires an explicit choice. After a pain event, the person must use the easy practice before starting a new chapter, so the pain guard is not reset.
- Approval checks the previous season, plan version, account time zone and preview start date under the account lock. The previous season closes only in the transaction that creates the next one.
- Finish for now remains a non-destructive stub in Step A; legacy season timing and milestone rules are unchanged. If an easy second-week rung is missing, the preview shows the approved first-week easy version, which matches the existing continuation behavior.

## Follow-up: weekly easy version, longer sessions, more questions

- The weekly AI draft was rejected with "bad weekly easy version" when any node's two-minute version was unsafe or malformed. That check is gone. `dropInvalidEasyVersions` deletes an unusable node or branch easy version before validation, and the client derives one from the first step (as it already did when the model omitted it). A plan is never lost over a bonus field. Tested in `tests/rolling.test.ts`.
- Daily budgets are now 5, 15, 30, 45 and 60 minutes. The same list is used by `BUDGETS`, `TIME_OPTIONS`, the duration clamp, the Edge allow-list and the database constraint/validator; the 30-minute fallback remains for unknown legacy values. Existing 5/15/30 plans are untouched and still valid. `202610280002_budgets_and_questions.sql` replaces the constraint and the two validator functions in place; it is a NEW migration and was not applied here.
- Personalization now accepts up to five questions and answers: the model prompt asks for three to five, `validateQuestions` accepts 1–5, the Edge Function forwards 5, the database wrapper and `set_personalization_context` accept 5, and `GENERAL_QUESTIONS` has 5. The consent copy already says "a few", so no new category of data is disclosed, but more answers may be sent once consent is given.
- Both database changes live in one new migration. `apply_all_stages.sql` now includes it (nine files) and `apply_remaining.sql` covers migrations 6–9. An existing project that already ran 6–8 must run only the new migration; the bundle aborts safely at the first duplicate. Tests cover both bundles and the new PGlite constraints/validators.
- The Edge validator rejected the entire draft with "bad focus" when a branch's display label (`focus`) exceeded 48 characters. A label is not a practice, so it is now trimmed at a word boundary by `normaliseFocusLabels`, missing or unusable labels are omitted, and the hard rejection is gone. The app already has a neutral fallback and truncates on its side. Tested in `tests/rolling.test.ts`.
- Not verified: the live Edge Function and Supabase database. The function must be redeployed and the migration applied before these limits take effect in production.

## Target-date change: who owns the stage dates

- A live attempt returned a good draft and was rejected with `invalid stage outline`, then the starter library was used. The validator demanded the model reproduce exact contiguous dates, which is arithmetic the app already knows how to do. The model now writes only stage titles and outcomes; `normaliseStages` places them on the canonical ranges for the leg. A wrong date, an inclusive end or one stage too many or too few no longer costs the person their AI plan.
- The prompt now lists the exact date ranges instead of asking the model to divide the days, so the common failure is avoided before the fallback does anything.
- Invalid or missing text for one stage becomes a neutral label for that range only; the other stages and every practice survive. Stage text still goes through `validatePracticeText`.
- A test pins the server's ranges to the app's `stageRanges` for every boundary length (14, 15, 28, 29, 56, 57, 112), so the outline and the pace line cannot disagree about the current stage. The strict `validOutline` helper was removed rather than left unused.
- The deployed function must be redeployed for this to take effect; the local tests exercise the new code path but no live plan was generated here.

## Target-date change: Stage 4 safety

- Existing accounts keep nullable age brackets and are asked on the next app session; no historical rows are rewritten. New auth.users inserts require an eligible self-declared bracket. This is tested in PGlite, not verified against live Supabase Auth; self-declared age cannot be verified. The bracket is immutable through the app RPC after first confirmation.
- High-risk and conservative physical initial plans deliberately use a fixed, labelled local preparation-only alternative even if AI drafting succeeds. This is smaller and safer than trusting model prose to avoid technical instruction. Ordinary physical goals still use normal drafting. Keyword classification is conservative but cannot recognize every possible wording; making a sport-related app/book alone is treated as making, while mixed goals retain physical flags.
- Screening answers remain transient component state. Only conservative_mode is included in plan storage; goal_category is stored separately as a category without duplicating goal text in logs. Flags only escalate. Weekly AI prompts inherit the persisted flags, and the existing output validators remain in place.
- Pain records a skipped event and no growth. A full event and accepted weekly detail are blocked until an easy practice is recorded. Replaying the same pain event after that easy practice must not pause progression again. This is not a medical clearance or diagnosis.
- The existing database-test auth.users stub gained raw_user_meta_data to test the real signup trigger shape. No previously saved season, event, migration or historical plan was changed.
- Phone checks: try under-13 signup, teen physical onboarding, adult physical screening yes/no, a Matterhorn goal, pain followed by easy practice, and signed-in legacy account age confirmation. No phone run, native build, deployment or remote migration has been performed.

## Target-date change: Stage 5 mid-week adaptation and trust fixes

- The tree copy now says what the code does: every tier is open and completing one keeps it grown. Milestones in this app are derived from milestone counts, not a lock chain, so making the tree sequential would have meant a new lock state and would have hidden practices the person already owns. The "Locked" legend was removed for the same reason: no node is ever locked here. This is the smallest truthful change.
- `QueueStore.write` now reports whether the device accepted the write. A failed local write is a new `unsaved` sync state, and no message outside the queued/idle states may contain the word "saved": the dashboard wording comes from `syncMessage` in `src/lib/sync-status.ts`, which is unit-tested for exactly that. When the write fails the event stays in the in-memory retry map with its original `client_event_id`, so the practice sheet can retry without double-counting.
- Mid-week offers are fixed rules in `src/lib/adapt.ts`, never model output: two consecutive skipped days (not rest days, not undone, not another season) offers the easier version for today, and three counted practices rated 4 or 5 inside the current seven-day block offers a lighter week. Offers are dismissible for the session and never applied automatically.
- The lighter-week offer uses a new owner-only RPC, `set_lighter_week`, because seasons are select-only for clients. It starts today rather than next week: `seasons` records only `week_mode_until`, so a future start would need another column. The window is capped at the leg boundary (`ends_on - 1`). This migration is written and tested in PGlite only; it is not applied to Supabase, so the offer's button reports a save failure until the migration is run.
- The pain pause suppresses both offers, because the easier version is already forced in that state.
- Phone checks for this stage: two skipped days then the easy offer, three hard ratings then the lighter offer, dismissing an offer, airplane mode with storage available, and a device that refuses storage (no "saved" wording anywhere). No phone run, build or deployment has been performed.

## Target-date change: Stage 6 release basics

- Support and privacy links are now `EXPO_PUBLIC_SUPPORT_URL` and `EXPO_PUBLIC_PRIVACY_URL`, with the old `example.com` values as the explicit placeholder fallback. The first version refused to start in development while either was missing; that was correct while the pages were being built but blocked everyday testing for a page that does not exist yet, so it was replaced: development logs one warning, and Settings shows either row as "page coming soon" instead of making a dead link tappable. The release checklist still requires both values before a store build, and `isPlaceholderUrl` is the single definition of a placeholder (not https, `example.com`, `your-domain`, or a `.example` host). Nothing in the app can invent a real page.
- The policy draft is `docs/PRIVACY_POLICY.md` ("draft, needs review"), written from the code: target date and leg length, personalization answers and their removal behaviour, weekly inputs sent for a proposal, reminder time and offline queue as device-only, age bracket as self-declared and unverifiable, and the screening answer as not stored. `docs/PRIVACY_DATA.md` remains the internal inventory.
- The device checklist is a separate file so it can be printed and filled in on the phone; it covers the date edge cases, the reminder permission states, pain, offline and deletion end to end. Notifications require a development build.
- The release checklist's migration list was stale (four files). It now names all eight migrations, and `supabase/apply_all_stages.sql` was regenerated from them: one transaction, in filename order, with a header warning that a project which already applied some files must run only the newer ones. A live project that hit "relation progression_config already exists" proved that warning was needed: the full bundle is for a new project only. `supabase/apply_remaining.sql` was added for the in-place upgrade, holding migrations 6–8 and a read-only query in its header that reports which of the three is still missing. Tests pin both bundles to the migrations (drift fails), apply the full one to an empty PGlite database and the remaining one on top of migrations 1–5, and require a second run to abort while leaving the first intact. The retention queries stay out of both bundles: they are repeatable analysis, not schema.
- TestFlight gaps were read from `eas.json`/`app.json` and listed, not fixed: no project link, no iOS submit credentials, a fixed build number with no auto-increment, no export-compliance answer, and store-side metadata. No build was run.

## Target-date change: Stage 7 retention queries

- The cohort excludes migrated accounts: a backfilled season is one with a `plan_versions` row whose snapshot says `source = migrated`. Those people used the old app, so counting them as new users who did not return would understate every rate.
- Day numbering is explicit in each file: day 1 is the first season's `started_on`, day 2 is the next calendar day (start + 1), day 7 is start + 6, week 1 is days 1–7 and week 3 is days 15–21. "Return" means a counted practice on that local date, never an app open.
- Eligibility uses `current_date` in UTC against the local `started_on`, so an account can be excluded for up to one day after its window has ended in its own timezone. Excluding a young account is safer than reporting a false churn.
- Onboarding completion is labelled a proxy everywhere: the first season created, because the app only calls `start_next_season` after onboarding and an approved preview. A person who abandons onboarding cannot be seen.
- "Still active in week 3" is a logged practice in days 15–21, not a session. Week 1 is reported both as any counted day and as the average count, because a single day in week 1 and five days in week 1 are different products.
- The files are not migrations and create nothing. They are plain SELECTs intended for the SQL editor with the owner role; the README states they must not be exposed through an RPC, view or schedule. A test executes all five against the migrated PGlite schema and checks the counts for one backdated account; the fixture writes events with SQL because the RPC correctly refuses events older than its own window, and that write is confined to the in-memory test database.

## Stage 1

1. Season dates are local calendar dates; ends_on is exclusive (started_on + 30). Events retain their derived local_date permanently. Timezone changes affect new events, not history. UTC is the explicit migration default because the original app never saved a timezone; users can change it later.
2. Migrated completions count as practiced days but earn no new XP. A single immutable legacy grant preserves the original profile XP exactly, including when it differs from completed-node count. New completions earn 10 XP; easy and full are equal. Old profile/node tables remain intact and read-only.
3. Missing historical metadata is labeled as unavailable, with local provenance. No attempt is made to claim old AI consent or recover an unsaved blocker. Missing completion timestamps use the original season start and are labeled as inferred; original rows remain available for review.
4. Streaks span seasons. A rest-only day preserves an existing streak but does not start one; at most two rest-only days in the trailing seven dates qualify. Completion days always qualify, including a day also marked rest. Rest awards no XP or milestone days. Today may still be unfinished: current streak remains visible if the latest qualifying date is yesterday.
5. Milestone unlocks are derived, not sticky stored awards; undo may remove a threshold. Supporting practices stay optional. One active season per user; archive preserves history and lifetime XP.
6. All client writes use owner-checking RPCs. Existing reward columns are retained solely for rollback/backfill, never updated by the new client. PostgreSQL configuration mirrors src/lib/progression.ts, verified by tests; the server is authoritative.
7. Stage branches intentionally require new migrations. A missing schema is an explicit retryable load error, never an empty-account signal and never a reason to overwrite a legacy tree. No production migration or deployment is performed.
8. Node's test runner via tsx and an embedded PostgreSQL (PGlite) are local development tools, not app/native runtime dependencies. They do not verify Supabase gateway/JWT integration or real-device behavior.

## Stage 2

1. The daily plan is built from the tree itself: each branch's first node becomes one practice, so the steps a person reads are the ones written for their goal. The curated library supplies any branch the tree did not cover, and the whole plan if the result would fail validation, so no plan can contain a step that exceeds the budget. This reverses the earlier rule that practices always came from the library — that rule guaranteed safety but made every plan for a theme identical, which is why a generated plan read as generic advice. The server still validates every generated practice, and `validatePlan` runs before the plan is saved. Recorded as `plan_source: ai` when AI contributed.
2. Theme detection is deterministic weighted keyword matching (strong term = 3, weak = 1) after lowercasing and simple stemming; ties resolve by a fixed theme order that puts specific themes first. Anything unmatched falls back to the universal consistency theme rather than guessing.
3. One template step list is used for all three budgets; the minutes attach from the budget and extra `deep` steps appear at 15 and 30 minutes, capped at five steps in total (`MAX_VARIANT_STEPS`). The cap is the same one `start_next_season`/`update_plan` enforce in SQL and the Edge Function applies to generated instructions, so a longer template fails a unit test instead of a save. This keeps 10 themes reviewable while guaranteeing no step prescribes more time than the chosen budget. Steps that mention time are rejected by `validatePlan` if they exceed the budget.
4. Replacement practices are drawn from three generic alternatives per branch, filtered against the practices already in the plan. A replacement keeps its branch and role and never rewrites past events.
5. Weekly review thresholds live in `src/lib/review.ts` and are mirrored in `submit_weekly_review`; unit tests pin the client boundaries and the SQL tests pin the server. The proposal is computed locally and shown before any write; only the confirmed outcome is stored.
6. `week_mode` (same/lighter) is the only persisted adaptation. "Lighter" preselects the easy variant for the following week through `week_mode_until`. Nothing is ever made harder automatically: an increase is an offer the user must act on by editing the plan.
7. Finishing a season always starts a new one, either continuing the same goal (new plan version) or with a new goal, so the app never leaves an account with no active season and a blank dashboard. The old season is archived by the rollover and listed under past seasons; it is never deleted.
8. Editing a goal or time budget writes a new `plan_versions` row, retires the old practices and rebuilds milestones. Milestones are derived (not sticky awards), so rebuilding them cannot lose earned XP or history; completion events keep pointing at the retired practice rows.
9. `NodeModal` was removed: the practice sheet replaced it, and leaving it in place would keep a second, contradictory completion path and developer wording in the codebase.
10. The blocker question offers seven answers, not four: no time, stress or low mood, and all-or-nothing were added because the original set assumed the problem was always motivation. Each blocker carries a `strategy` used by the local plan and its own instruction line in the AI prompt (`blockerStep`), so a new blocker cannot be stored and then ignored.

## Stage 3

1. Safety rules live in `src/lib/safety-rules.ts` with no dependencies. A generated copy in the Edge Function folder is produced by `npm run safety:sync`, and a test fails when the copies differ. The Supabase bundler cannot reliably import outside its own folder, so a checked copy is safer than a shared import.
2. Recovery goals take the support path before any substance rule, so "quit cocaine" is never treated as an error. Only self-harm intent stops plan creation, and it shows crisis resources instead.
3. Output validation is applied to every generated node on the server, and again on the client in `sanitizeGeneratedNode`, so a compromised or stale function cannot bypass it. Steps that mention more minutes than the budget are rejected.
4. Consent is versioned (`AI_CONSENT_VERSION`). A consent record with a different version does not count. Declining or withdrawing never removes a feature: the local library builds the same shape of plan with `allowAi: false`, so no AI call is made at all.
5. Email verification is controlled by `EMAIL_VERIFICATION_REQUIRED`, default `false` because the project setting is not known from code. The sign-up flow already handles both cases (session returned, or "check your inbox"), and resend is available from the sign-in screen. Change the constant if the project requires confirmation.
6. Account deletion runs in an Edge Function that verifies the caller's JWT and then deletes the auth user with the service role; all app tables cascade. The app clears its local session afterwards. The function is written but not deployed.
7. Offline events are stored per user in AsyncStorage with their original `client_event_id`, replayed on foreground and after load, and removed only on success. A replay failure keeps the entry and increases its backoff; a success that the server recognises as a duplicate is treated as success, so nothing is double-counted.
8. When an event is queued offline, the practice sheet closes and the dashboard shows a real "saved on this device" state instead of demanding a retry that would fail again.
9. Lint failures were fixed at the cause: React Native's `useAnimatedValue` replaces reading `useRef(...).current` during render, unused imports were removed, and a helper named like a hook was renamed. No lint rule was disabled and no suppression was added.
10. The generation quota is 20 per user per local day, incremented atomically in SQL. Model names come from `GEMINI_MODEL` (with `gemini-2.5-flash` as the documented fallback) instead of a hard-coded list, and upstream errors are logged server-side while the client receives a generic message.
11. Support and privacy URLs remain clearly marked placeholders in `src/lib/config.ts`; no URL was invented. The two-account RLS script is committed but not run, because no test accounts exist in this environment.
12. Password recovery handles both Supabase link styles (PKCE `code` and implicit `access_token`) through one parser, so the flow works whether or not PKCE is enabled in the project.
13. The AI consent decision is asked at the start of onboarding, before the identity question, not when the plan is built. Asking it at the plan step interrupted the moment the user expected their plan and read as a stumble in the flow. The trade-off is that the sheet lists what will be sent before the goal has been typed; the copy is phrased in the future tense for that reason. Dismissing the sheet is treated as declining, so an unanswered choice can only ever produce the on-device plan and never an AI call.

## Stage 4: the plan engine

1. Generated plans used the curated library even when the model ran: only `tree.summary` and the branch focus labels survived, so "use AI" and "build on this device" produced identical steps. That was too safe. The plan now uses the tree's own practices, with the library as a per-branch and whole-plan fallback, and `validatePlan` still runs before anything is saved.
2. The whole tree is used, not one node per branch. Branch nodes 1-4 are weeks 1-4 of that branch's practice, stored as an optional `ladder` array inside the existing `full_variant` jsonb. Nothing is lost, and a practice deepens instead of asking for the same first action for thirty days. This needed no migration: the SQL plan validator checks that required keys exist, never that extra keys are absent, and `install_practices` copies the variant verbatim.
3. The week is derived from `seasons.started_on` and the profile timezone through `planWeek`, so the ladder advances on the calendar the person actually lives in. A short or missing ladder holds its last real rung rather than jumping backwards.
4. The two-minute version is now written by the model per branch (`easy`), validated when present and never fatal when absent: the client falls back to the practice's first step. The old derived version ("step one, then stop") is still the floor, not the target.
5. A finished season briefs the next plan. `planHistory` sends only numbers and short strings: days practised, which practices stuck, which never happened, average effort, and the last review note. The Edge Function clamps every field again, so the client cannot widen the payload. Nothing new is stored and no new data leaves the device that the person did not already record there.
6. Editing a goal or time budget now regenerates through the same engine instead of rebuilding from the library. "Choose a new goal" after a season does the same. The previous behaviour would have silently replaced personalised practices with shared templates at exactly the moment the person asked for a change.
7. The local (no-AI) plan is still template content with the person's goal woven in. It cannot invent steps for an unfamiliar goal without a model; it exists as the consent-free and offline path, and the prompt work above does not pretend otherwise. It also has no week-to-week ramp, because a library practice has no honest fourth-week version to offer.
8. `tests/plan-matrix.test.ts` walks eighteen goal shapes (running, strength, sleep, food, study, coding, writing, stress, family, vague) through theme detection, the plan builder and the tree adapter, and asserts the same contract for each. It immediately found three real misclassifications: "fall asleep before midnight" fell back to the generic theme because "asleep" and "midnight" were not terms; "call my sister" did the same for lack of family words; and "keep a habit" was scored as a food goal because "habit" was a nutrition weak term. The terms were corrected rather than the expectations relaxed.
9. Placeholder wording is now rejected by the server with one corrective retry, because a prompt alone did not stop the engine repeating "reset your shoulders". The list is deliberately narrow: phrases that are placeholders in every context. "Roll your shoulders once and begin", which the study theme uses as a real setup step, is allowed, and breathing work is untouched so a mindfulness goal is not blocked by the guard meant to protect it.
10. The default body branch was rewritten for sitting, thinking goals: leave the screen, move, and come back with the next step decided, in one coherent ramp. The previous version opened with a posture-and-breath reset and then jumped to a movement circuit, which was neither a ramp nor tied to the goal. The coding theme's body practice changed for the same reason.
11. The plan preview now shows what the plan promises rather than a fixed sentence: the plan's own summary, the first action of the daily practice, and the week-4 step that the 30 days lead to. The summary field was always generated and stored and was never displayed, which made a personalised plan look like a generic one at the only moment the person is deciding whether to trust it.
12. A weekly review that asks for a lighter week still shows the current week's rung of the ladder with the easier version preselected; it does not roll the practice back a week. That keeps the ramp monotonic and leaves the choice with the person, which matches how the review already behaves elsewhere.
13. Theme detection now reads intent before vocabulary. `intendedTheme` looks for a making verb and an artefact noun (or an artefact plus "helps people"); if the artefact is digital the goal is coding, if it is text or a performance it is writing. Without this, "make an app that helps people eat healthier" scored on the words "eat healthier" and planned the person's own cravings — the exact plan they did not ask for. Negative cases are pinned in tests: "eat healthier every day" and "design a meal plan for my family" stay nutrition, and "read one book a month" stays study because reading a book is not making one.
14. The coding theme is written for an empty repository: the daily practice names the next piece, opens the file, builds it and runs it, rather than assuming a project that already opens. Its connection practice became a user interview — asking one person what they do now — because "show what you made" is impossible in week one of a build and research is the step that actually improves the product.
15. The client sends the detected focus label and primary branch with the generation request. The Edge Function validates the branch against the four known values and the prompt states that a craft goal is about the artefact, not the person's own health. This is advisory context for the model, not a safety boundary: the safety checks remain independent of it.
16. The fallback is no longer silent. `fallbackReason` (in `src/lib/engine/fallback.ts`, so it is testable without a Supabase client) distinguishes permission off, quota, a rejected draft and an unreachable function, and the onboarding preview states which one happened, with a retry. Two plans in a row were judged as if they were the model's when they were the on-device library, and nothing on screen said so; that is a product defect in its own right, not just a debugging inconvenience.
17. The Edge Function now answers 503 when it never received a draft and 502 only when a draft arrived and was rejected, so that message can be accurate instead of blaming the safety checks for a network failure.
18. For a building goal the prompt now assigns each branch a job — craft is the build, mind is research and decisions, connection is testers and launching, body is the routine that makes a thirty-day build survivable — and requires the four weeks to tell one story: understand the problem, build the smallest usable version, put it in front of someone, then improve or show it. "Open the editor" joined the filler list. Without this the plan was advice about being productive rather than a plan for the product.
17. The primary branch is no longer "one practice deepened for four weeks". For a goal that is an artefact, the four rungs are the four stages of the work: find out, make the smallest real thing, put it in front of a real person, respond. The previous rule ("never a different activity") was the reason a build plan read as four repetitions of "work on it" — the structure itself forbade the plan from moving from research to build to testers. Supporting branches keep the deepening rule, because a weekly support practice should deepen rather than change.
18. The model is now asked to complete a short research pass before writing any practice, returned as `brief` inside the same JSON: the outcome, the method by name, what the first week looks like, how this goal usually fails, and what must be researched and where. It conditions the plan in the same call instead of a second request, which keeps one quota unit and one timeout. The brief is not persisted or displayed: storing it would need a migration plus a screen, and the promise it enables is already carried by `plan_summary`, the practice `why` and the ladder.
19. The client sends a starting-point hint (nothing / exists / practice) inferred from the goal text in `src/lib/engine/stage.ts`, and the prompt turns it into a sentence. It is advisory, never a restriction: the model is told to follow the goal if it disagrees. Without it, week 1 of "build an app" and week 1 of "get users for my app" are written identically, which is the difference between research and retention work.
20. Specificity is enforced, not requested. The placeholder list grew (five lines, open the editor, work on your project, make progress, save your progress, celebrate, stay consistent) and a step repeated across two branches is rejected as a step written for neither. Both failures trigger the existing single corrective retry, which now names the exact offending wording. The list stays narrow on purpose: breathing and shoulder work remain allowed, because a mindfulness or desk goal needs them.
21. `npm run typecheck:functions` was added, and CI runs it. The Edge Function sits outside the TypeScript project, so a template literal containing a stray backtick passed typecheck, lint and tests and would only have failed at deploy. The new script compiles both functions with the Deno global suppressed by their existing `@ts-expect-error` lines.
22. The on-device coding plan now carries the same arc (draw one screen, make it work end to end, three testers, fix their stuck point), and its summary states the promise instead of describing the person ("Built for a Creator working toward…"). The local path still cannot invent domain steps for an unfamiliar goal; it is now honest scaffolding rather than a plausible-looking product plan.
23. A drafted plan is now repaired one branch at a time instead of being thrown away whole. `validatePlan` used to run after assembly, and any single problem — one step naming more minutes than the budget was the common one — replaced all four drafted branches with the curated library while the season still recorded `plan_source: ai`. That is a plan that looks like a template while claiming to be drafted, and no screen or log said so. Branches are now validated individually with `validatePractice`, a broken branch alone falls back, and `plan_source` is the tree's source gated by whether any drafted branch survived, so an on-device tree can never be labelled AI. A repair or a full fallback writes one line to the Metro console, so the difference between "the model wrote something generic" and "the model's plan was discarded" is visible without a database query.
24. Settings now shows where the stored plan came from: the plan source, its version, and what to do about it. The onboarding preview only describes the plan being built; once saved, nothing in the app answered "did the AI actually write this?", which is why the question kept coming back.
25. The Edge Function logs one line per attempt with the attempt number, the model name and the validation verdict (never the goal text). That makes "did the model run?" answerable from the function logs, and separates an unreachable model from one whose draft was rejected.
26. The model call's failure is no longer swallowed. `callModel` returned null for every non-200, so an invalid key, an exhausted free quota and a network fault all reached the app as "the AI could not be reached" — three different fixes behind one sentence. The upstream status and the provider's own short message are now logged and returned as `detail` (the API key is redacted from it), and the validation problem is returned instead when the draft itself was rejected.
27. The onboarding preview no longer presents a starter plan as the plan. When the draft did not come from the model, a bordered panel says "This is not an AI plan", names the specific reason, shows the server's detail line, and the main button becomes "Try the AI again" while using the starter plan is a separate explicit choice. A local fallback that looks like a personalised plan is worse than an error, because it teaches the person to distrust the product rather than the connection.
28. The app's own plan source is shown in Settings and the onboarding preview, and `plan_source` is now derived from the tree's real origin, so the label cannot claim AI work that the library did.
29. Sport names (tennis, soccer, swimming, cycling and the rest) were added to the strength theme and to the on-device theme detector. A tennis goal previously fell through to the generic desk plan, which produced "two minutes away from the screen" for someone who wanted to play better tennis.
30. The plan function now asks for `gemini-3.8-flash`, with `gemini-3.6-flash` and `gemini-3.5-flash-lite` behind it in an ordered list. Google restricted 2.5 Flash to accounts that had already used it, so a new key answered 404 "no longer available to new users" and every plan fell back to the on-device library. Only a missing or retired model name moves to the next entry; an invalid key or a spent quota stops at the first attempt, because trying three names would just repeat the same error more slowly. `GEMINI_MODEL` still overrides the list for pinning a specific model.
31. A test pins the model list and the release checklist to a current name, because this failure is invisible from the app: the plan still arrives, still looks plausible, and is simply written by the wrong author.
32. The model call gets its own 60-second budget, separate from the 15 seconds used for auth and REST. Sixteen practices is a long generation, and a 15-second abort on a healthy reasoning model surfaced as "the request to the model failed" — the one failure the app could not explain, because it came from a thrown abort rather than a provider response. A thrown fetch is now described as "timed out after 60s" or "network: …", a timeout or dropped connection is not retried (it would not differ, and two of them would outlast the function's wall clock), and the loop refuses to start a second attempt past 90 seconds for the same reason.
33. Each successful or rejected attempt logs its elapsed time. Latency, not just correctness, is what decides whether a 30-second planning screen is acceptable, and the log is the only place that number exists.
34. The model call asks for `thinkingConfig: { thinkingLevel: "low" }`. Gemini 3 models think at high effort by default, and this request is a long structured answer rather than a hard reasoning problem: high thinking alone can outlast the whole budget, which is exactly what the 60-second timeout caught. If a provider ever rejects the field with a 400 that mentions thinking, the same request is retried once without it, so an unknown option cannot cost the person their plan. The model budget is 75 seconds now, and a second attempt is only started before the 60-second mark so two attempts cannot exceed the function's wall clock.
